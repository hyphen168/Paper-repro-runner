# 论文复现助手需求分析文档

## 1. 项目背景

随着科研工作日益依赖代码复现，研究人员常常面临以下问题：

- 论文链接与代码仓库之间缺乏直接映射
- 代码复现需要大量环境调试，耗时长且容易失败
- 真实执行过程通常需要云端计算资源，而用户本地又希望保留控制权与数据
- 研究人员容易在环境适配、日志回看、结果整理等环节浪费大量时间
- 面试、汇报或项目展示缺少一个能体现工程能力的产品化展示形式

本项目围绕“轻量化论文复现助手”这一目标设计，力求将“论文到代码到复现”的过程抽象为一个工程化工作流，并为用户提供更好的使用体验与项目展示能力。

## 2. 目标用户

### 2.1 典型用户画像

- 学术研究者
  - 想复现论文代码，但缺乏稳定环境和统一流水线
- 计算机视觉 / AI 学习者
  - 想从论文中学习并尝试复现实验，但不希望被环境问题卡住
- 学生与项目参与者
  - 需要一个具备工程展示感的论文复现工具，用于项目和面试表达
- 小型团队 / 个人开发者
  - 希望把云端执行资源用于重计算，同时保留本地控制和本地数据

### 2.2 用户痛点

- 论文网址和源码仓库不一一对应，人工检索耗时
- 环境要求不一致，Python 版本、依赖、CUDA 常常造成复现失败
- 一旦复现失败，日志难以追踪和复盘
- 官方代码可能没有完整说明，导致难以启动
- 用户希望“本地保留数据、云端做重计算”，但缺少可落地的工具架构

## 3. 产品目标

### 3.1 核心目标

- 降低论文复现门槛，减少环境调试成本
- 使用本地控制端 + 云端执行端的架构，提高可扩展性
- 将任务执行过程结构化，以便复盘、展示和后续迭代
- 通过智能分析，帮助用户从论文和仓库中抽取创新点、风险和结论
- 为 GitHub、项目展示、面试汇报提供完整材料

### 3.2 业务价值

- 让研究型工作从“脚本式复现”变成“流程化复现”
- 把环境和代码执行分层处理，提升工程质量
- 让用户更容易理解复现过程与价值点
- 形成可展示的科研工程化作品

## 4. 用户需求概述

### 4.1 功能型需求

1. 用户输入论文链接
2. 系统尝试从论文页面识别代码仓库地址
3. 用户可以补充或修正代码仓库候选
4. 用户提供云服务器信息与 SSH 密钥
5. 系统支持本地保留任务和日志
6. 系统自动检测 Python、依赖、环境类型
7. 系统执行远程复现流水线
8. 系统记录执行日志和状态
9. 系统根据论文、仓库和日志做创新点分析
10. 系统生成 Markdown / JSON 报告
11. 系统提供 GitHub-ready 项目总结
12. 系统支持本地和同网段移动端访问

### 4.2 非功能需求

- 本地轻量：尽量减少依赖和部署复杂度
- 数据局域化：核心数据保留在用户本地
- 稳定性：避免 SSH 环境连续性断裂
- 易用性：适合非技术用户快速上手
- 可扩展性：可继续接入更多算法、更多任务类型
- 适配性：支持 conda / venv / docker 等常见方案

## 5. 关键场景

### 场景一：论文链接转代码仓库

用户输入论文链接，系统尝试抓取页面文本，并从中筛选 GitHub / GitLab / Hugging Face 等候选链接。若未识别成功，用户可手动补充。

### 场景二：云端执行

本地应用提交复现任务到用户自有云服务器，后台拉取代码、创建环境、安装依赖、执行验证脚本，并返回日志。

### 场景三：环境诊断

在执行前，应用识别仓库使用的是 requirements.txt、environment.yml、Dockerfile 还是工程安装方式，并推荐最佳运行环境。

### 场景四：结果分析

系统根据论文页、仓库说明和日志分析潜在创新点、主要风险和可能结论，提升复现后的可解释性。

### 场景五：成果展示

系统自动生成任务报告、实验对比表和项目总结，方便直接提交到 GitHub 或用于面试说明。

## 6. 功能需求细化

### 6.1 任务输入模块

- 输入论文 URL
- 可选输入代码仓库候选
- 配置云服务器地址、用户名、SSH 私钥位置
- 配置远程工作目录
- 配置本地数据目录

### 6.2 任务执行模块

- 自动创建或切换运行环境
- 自动拉取仓库代码
- 自动安装依赖
- 自动执行测试验证
- 自动回收日志与状态

### 6.3 任务管理模块

- 任务创建
- 任务状态变更
- 日志追加
- 当前步骤查看
- 历史任务列表

### 6.4 智能分析模块

- 文本关键词分析
- 仓库文档与论文文本对比
- 可能创新点归纳
- 风险评估
- 复现结果总结

### 6.5 报告输出模块

- Markdown 报告
- JSON 结构化结果
- 项目总结文件
- 实验对比表

## 7. 非功能需求细化

### 7.1 易用性

- 支持本机首次启动自动创建虚拟环境
- 支持直接双击启动器、无需复杂命令行
- 支持同网段手机访问

### 7.2 安全性

- 本地保留配置与日志
- 不将密钥写入仓库
- 云端仅用于计算，不承担本地数据持久化

### 7.3 可靠性

- 避免单步 SSH 环境丢失
- 对流程步骤有清晰结构化表达
- 允许继续扩展更多严密的错误重试逻辑

## 8. 未来扩展方向

- 接入更强的自动化诊断器，检测依赖冲突和 Python 版本不兼容
- 接入更丰富的论文抓取能力，支持更多研究平台
- 强化云端日志实时流式展示
- 提供任务重试与失败恢复机制
- 扩展到更通用的科研复现平台范式

## 9. 结论

该项目的核心价值在于把“论文复现”从零散脚本工作流升级为一个具有工程化结构、产品化展示和科研复现思维的本地控制应用。它既服务于实际科研复现，也具备展示产品能力，适合用于项目展示、面试表达和 GitHub 提交。

其设计逻辑符合真实科研场景，也保留了学习、扩展和落地的空间，属于一类“实用但具备成长潜力”的产品型工具。
